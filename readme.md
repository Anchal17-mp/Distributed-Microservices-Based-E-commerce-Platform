# Bazaario — Distributed Microservices E-Commerce Platform

A multi-vendor e-commerce marketplace built with a **distributed microservices architecture** using Django REST Framework, MySQL, Docker, and a vanilla JavaScript frontend.

The project demonstrates how an e-commerce application can be divided into independent services, where each service owns its own database and communicates with other services through REST APIs.

The frontend communicates with the backend through a centralized **API Gateway**, providing a single entry point to the entire application.

### Supported Roles

* **Customer** — Browse products, manage cart, checkout, make payments, and track orders.
* **Vendor** — Add and manage products, manage inventory, and fulfil orders.
* **Admin** — Approve vendors, manage users, and moderate products.

## Architecture

```text
                         ┌──────────────────────────┐
                         │        Frontend           │
                         │ HTML / CSS / JavaScript   │
                         └────────────┬─────────────┘
                                      │
                                      │ HTTP :8080
                                      ▼
                         ┌──────────────────────────┐
                         │       API Gateway         │
                         │     Port: 8080            │
                         │   Request Forwarding     │
                         └────────────┬─────────────┘
                                      │
                ┌─────────────┬───────┼────────┬─────────────┐
                │             │       │        │             │
                ▼             ▼       ▼        ▼             ▼
        ┌────────────┐ ┌──────────┐ ┌──────┐ ┌─────────┐ ┌─────────┐
        │ Auth/User  │ │ Product  │ │ Cart │ │  Order  │ │ Payment │
        │  Service   │ │ Service  │ │Service│ │ Service │ │ Service │
        │   :8000    │ │  :8001   │ │ :8002 │ │  :8003  │ │  :8004  │
        └─────┬──────┘ └────┬─────┘ └──┬───┘ └────┬────┘ └────┬────┘
              │             │           │           │           │
              ▼             ▼           ▼           ▼           ▼
        ┌──────────┐  ┌───────────┐ ┌────────┐ ┌─────────┐ ┌──────────┐
        │ user_db  │  │ product_db │ │cart_db │ │order_db │ │payment_db│
        └──────────┘  └───────────┘ └────────┘ └─────────┘ └──────────┘
```

Each backend service is an independent Django project with its own MySQL database.

Services do **not directly access each other's databases**. When one service needs information owned by another service, it communicates with that service through its REST API.

JWT tokens are propagated between services so that downstream services can verify the original user's authentication.

| ------------------- | ---: | ------------ | --------------------------------------------------------------------------------------- |

# Key Architectural Concepts

## 1. Database Per Service

Each microservice owns its own database.

```text
Auth Service     → user_db
Product Service  → product_db
Cart Service     → cart_db
Order Service    → order_db
Payment Service  → payment_db
```

A service never creates a real foreign-key relationship with another service's database.

Instead, cross-service references are stored as logical IDs and validated through REST API calls.

---

## 2. Stateless JWT Authentication

JWT authentication is used across the microservices.

The services share the same JWT secret so that a token generated by the Auth Service can be verified by other services without querying the user database.

The JWT contains information such as:

```text
user_id
role
email
```

Other services build a lightweight user representation from these claims.

---

## 3. API Gateway

The frontend communicates with the API Gateway instead of communicating directly with individual backend services.

```text
Frontend
   ↓
API Gateway :8080
   ↓
Backend Services
```

The Gateway acts as a reverse proxy and forwards requests to the appropriate service.

It does not contain business logic or its own database.

---

## 4. Token Propagation

When one service needs to communicate with another service, the original user's JWT is forwarded with the request.

For example:

```text
Customer
   ↓
Frontend
   ↓
Order Service
   ↓
Product Service
```

The Product Service can verify the same JWT and process the request on behalf of the original user.

---

## 5. Live vs Snapshot Data

The project intentionally uses two approaches to data consistency.

### Cart

Cart information is fetched live from the Product Service.

This means the cart can reflect the current:

* Product price
* Product stock
* Product availability

### Orders

Order information is stored as a snapshot when the order is created.

For example:

```text
OrderItem.product_name
OrderItem.price
Order.shipping_address
```

This ensures that historical orders do not change when a product or address is later modified.

# Running with Docker Compose

Docker Compose is the recommended way to run the complete application.

## 1. Clone the repository

```powershell
git clone https://github.com/Anchal17-mp/Distributed-Microservices-Based-E-commerce-Platform.git
```

Move into the project directory:

```powershell
cd Distributed-Microservices-Based-E-commerce-Platform
```

---

## 2. Create the Environment File

Create a `.env` file in the project root.

Example:

```env
MYSQL_ROOT_PASSWORD=your_mysql_password
JWT_SECRET_KEY=your-long-random-jwt-secret
GATEWAY_SECRET_KEY=your-other-random-secret
```

### Important

Do not commit your actual `.env` file to GitHub.

Use `.env.example` to document the required environment variables.

---

## 3. Start the Application

Run:

```powershell
docker-compose up --build
```

Docker Compose will:

1. Build the backend service images.
2. Build the API Gateway.
3. Start MySQL.
4. Create the required databases.
5. Wait for MySQL to become healthy.
6. Run Django migrations.
7. Start all backend services.

The services will be available internally through Docker networking.

# Payment System

The Payment Service uses **simulated payments**.

No real payment provider such as Razorpay or Stripe is integrated.

The service simulates a successful transaction, generates a transaction reference, and updates the order status.

This approach is intentionally used for this student/learning project.

# Important Project Characteristics

## Independent Services

Each service can be developed and maintained independently.

```text
Auth
Product
Cart
Order
Payment
```

Each service owns its own data.

---

## Service-to-Service Communication

Services communicate using HTTP REST APIs.

For example:

```text
Order Service
      │
      ├──→ Cart Service
      │
      └──→ Product Service
```

There is no direct database access between services.

---

## Docker Networking

Inside Docker, services communicate using Docker service/container names instead of:

```text
127.0.0.1
```

Environment variables are used to configure service URLs so that the same application can work both locally and inside Docker.

# Known Limitations

This project is designed as a learning project, so some production-level features are intentionally simplified.

### 1. Separate Local and Docker Databases

The local MySQL environment and Docker MySQL environment use separate databases.

Switching between them means working with different sets of data.

---

### 2. Best-Effort Inter-Service Calls

Some inter-service operations are currently best-effort.

For example, during checkout, stock-decrement and cart-clear requests can fail if a downstream service is temporarily unavailable.

A production system could use:

```text
Celery
RabbitMQ
Message Queues
Retry Mechanisms
```

for more reliable asynchronous communication.

---

### 3. Simulated Payments

Real payment gateways are not integrated.

The Payment Service only simulates successful payment processing.

---

### 4. JWT Auto Refresh

Access tokens expire after approximately 60 minutes.

The frontend currently requires the user to log in again after token expiration instead of automatically refreshing the token.

---

### 5. Docker ALLOWED_HOSTS

The Docker configuration uses:

```python
ALLOWED_HOSTS = ['*']
```

because the services are intended to communicate internally through Docker/Gateway in this project.

For a production deployment, exact allowed hostnames should be configured.

---

# Security Considerations

The project uses JWT-based authentication and environment variables for sensitive configuration.

Do not commit:

```text
.env
```

to GitHub.

Sensitive values such as:

```text
MYSQL_ROOT_PASSWORD
JWT_SECRET_KEY
GATEWAY_SECRET_KEY
```

should remain private.

Only placeholder values should be included in:

```text
.env.example
```
